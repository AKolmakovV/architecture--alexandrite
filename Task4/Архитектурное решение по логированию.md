# Мотивация

Трассировка и логирование тесное переплетается друг с другом, одно дополняет другое, и если трассировка позволяет нам понять цепочку, движение запроса, то логирование позволяет лучше разобраться в том что происходит внутри каждого сервиса. Так мы сможем понять не только о том что у нас проблемы с сервисом, но и где именно, почему они возникают. Эта ценная информация даст нам следующие возможности:

1. Сэкономить время на поиск проблем
2. Эффективно решать возникшие проблемы, визуализируя происходящее внутри сервиса
3. Предотвратить возникновение проблем путем исправления либо доработки кода

# Предлагаемое решение

Логирование требуется для всех сервисов, но логировать следует рационально, для этого мы разделим логи на следующие типы:

FATAL - полный отказ в работе сервиса
ERROR - логирование ошибок, включено постоянно
WARNING - позволяет обратить внимание на места возникновения потенциальных проблем, данным статусом мы помечаем некритичные в работе приложения ошибки, нештатные ситуации, подозрительные активности и т.д. включено постоянно 
INFO - средний уровень логирования, подходит для мониторинга работы приложения, что бы понимать ход выполнения программ, не содержит технических деталей
TRACE - максимально детальная информация о каждом шаге выполнения, включается в исключительных ситуациях
DEBUG - логирование информации полезной для разработчиков, включается на время отладки

Примером рационального использования логирования может послужить отключение уровня DEBUG и TRACE логов, для всех сервисов на проде, включаем только на период отладки разработчиками, TRACE может быть включено для наблюдения за проблемным сервисом.

Также есть смысл настроить автоматическое ротирование, и ограничить размер собираемых логов, положительно повлияет на работу системы если ввести коды ошибок, мы сделаем меньше объем информации для хранения, и сможем проводить поиск по кодам для корелляции событий.

На Dev стендах имеет смысл включить DEBUG и TRACE, эта информация может быть полезной.

## Какая информация интересует для уровней WARNING, INFO:

1. Движение заказа и операции над ним
   1. Время события
   2. Идентификатор покупателя
   3. Номер заказа
   4. Статус заказа
2. Движение файлов моделей в системе и операции над ними
   1. Время события
   2. Идентификатор файла
   3. Идентификатор пользователя
   4. Наименование операции над файлом (загружен, начало расчета стоимости, сохранение в хранилище, ...)
3. Критически важные операции (прим. расчет стоимости заказа)
   1. Время события
   2. Номер заказа
   3. Название операции в расчетах
4. Действия пользователей в системе
   1. Время события
   2. Идентификатор пользователя (если есть)
   3. IP пользователя
   4. Информация о действии

## Компоненты сбора логов

Для сбора логов мы будем использовать Elastic Stack

1. Filebeat — это легковесный агент для сбора и передачи логов
2. Logstash — инструмент для сбора, обработки и хранения данных из журналов в различных системах
3. Elasticsearch – открытая распределенная система управления данными и поиска по ним
4. Kibana – это инструмент визуализации и анализа данных, который позволяет создавать интерактивные дашборды, графики и отчеты на основе данных, хранящихся в Elasticsearch
5. ElastAlert – система оповещений по отклонения в работе и критическим событиям

ElastAlert добавить важно, для эффективного реагирования на нештатные ситуации.

## Правила безопасности:

1. Требуется организовать защиту от несанкционированного доступа к логам
2. Обязательно шифрование критически важных для безопасности  или приватных данных в логах
3. Организовать контроль целостности лог-файлов
4. Организовать защиту от удаления или модификации логов

## OpenSearch

1. Лицензия: Open-source (Apache 2.0)
2. Сообщество и доступность документации: Большое и активное сообщество разработчиков и подробная документация на официальном сайте

Минусы: дорогая лицензия, по сравнению с ELK хуже справляется с большими объемами данных, считается что масштабирование Splunk весьма затратное, а поддержка у Splunk ограничена платным уровнем, по сравнению с ELK, OpenSearch меньше встроенных интеграций с бесплатными решениями, а также Splunk не такая производительная как тот же ELK


# На всякий случай сравним ELK и OpenSearch отдельно

Выбирать ELK если:
   * Требуется коммерческая поддержка
   * Нужны продвинутые ML-функции
   * Готовы платить за расширенный функционал
   * Важна стабильность и зрелость экосистемы

Выбирать OpenSearch если:
   * Приоритетна открытость и независимость
   * Требуется полный доступ к функциям без оплаты
   * Важна экономическая эффективность
   * Готовы работать с развивающейся экосистемой

Кажется, разумено доучиться и использовать OpenSearch в аналогичных нашим условиях, но для решения данной задачи я отталкиваюсь от своей личной осведомленности и опыта.
